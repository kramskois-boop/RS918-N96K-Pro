# Загрузчик UHSDR 5.0.4 в RS918 N96K-Pro

Загрузчик — первая программа, которую выполняет STM32F407 после включения (адрес `0x08000000`).
Он либо сразу передаёт управление прошивке, либо (по удержанию кнопки при включении) даёт обновить
прошивку с USB-флешки или перейти в ROM-DFU STM32. Документ описывает **UHSDR bootloader 5.0.4**
продукта (патч P2-1): состав, проверку версии, обновление загрузчика и прошивки, действия при сбоях.
Сборка загрузчика — [docs/BUILD.md](BUILD.md) §5.2; правила безопасности — [docs/SAFETY.md](SAFETY.md)
§2 и §7; состав релиза — [docs/RELEASE.md](RELEASE.md).

> **Статус:** загрузчик 5.0.4 **уже установлен на проверенном RS-918 и работает** (System Info →
> Bootloader `5.0.4`) — **не прошивать без необходимости**; если всё же обновлять, только
> программатором и имея план восстановления. Загрузчик **4.1.2** остаётся known-good. В пакете
> `release/bench-2026-11-27` лежит known-good образ 5.0.4 (31 620 Б, GCC 15.2.1); при полной
> CLI-сборке на **GCC 9.3.1** загрузчик собирается **32 416 Б** (CI/Docker, в пакет не входит).
> **Важно:** зависают не загрузчики, а **прошивки**, собранные GCC 15.2.1 (splash → кратковременно
> UI → зависание); для прошивок обязателен GCC 9.3.1 (docs/BUILD.md §1.1).

## 2. Карта flash

MCU стартует с `0x08000000`, поэтому загрузчик занимает первые 32 КиБ, а прошивка начинается с `0x08010000`
(`MCHF_FLASHRESERVED = 64` КиБ, `mchf-eclipse/src/bootloader/flash_if.h:46,58`; скрипты линковки:
`linker/arm-gcc-link-bootloader_f4.ld` — rom `0x08000000`, 32k; `linker/arm-gcc-link_f4_flash1024k.ld` —
rom `0x08010000`, 960 КиБ).

| Область | Адрес | Размер | Содержимое |
|---|---|---|---|
| Загрузчик | `0x08000000`–`0x08007FFF` | 32 КиБ | код 5.0.4: known-good 31 620 Б (пакет), GCC9 all-сборка 32 416 Б (CI, в пакет не входит) |
| Конфигурация | `0x08008000`–`0x0800FFFF` | 32 КиБ | эмуляция EEPROM (`USE_CONFIGSTORAGE_FLASH`; `EEPROM_START_ADDRESS = 0x08008000`, `misc/v_eprom/eeprom.h:40`). Загрузчик эту область **не стирает** |
| Прошивка | `0x08010000`–`0x080FFFFF` | 960 КиБ | GCC9 default: 312 216 Б (31,8 %), запас 670 824 Б; v1.2 (GCC15, невалидна) — 321 392 Б |

Практические следствия:

* обновление прошивки не затрагивает загрузчик и настройки — стираются и пишутся только секторы от
  `APPLICATION_ADDRESS = 0x08010000` (`mchf-eclipse/src/bootloader/command.c:245-255`);
* обновление **загрузчика** трогает только первые 32 КиБ; при неудаче прошивка физически остаётся
  на месте, но запустить её без целого загрузчика нельзя (`BAND+`/`BAND−` обрабатывает сам загрузчик).

## 3. Что изменилось в 5.0.4 относительно 4.1.2

Портированы 8 файлов из upstream UHSDR 2.12.2 (`dcbebe5f`, суммарно +164/−103 строк):
`bootloader_main.c/.h`, `command.c/.h`, `flash_if.c/.h`, `uhsdr_boot_hw.c/.h`.
6 из 8 файлов совпадают с upstream байт-в-байт (с точностью до EOL), 2 файла — upstream плюс
адаптации под дерево 2.9.48 (маркер `N96K P2`):

* `bootloader_main.h` (+7 строк) — псевдонимы старых точек входа (`bootloader_main`, `BL_Application`,
  `mchfBl_CheckAndGoForDfuBoot`), потому что `basesw/mcHF/Src/main.c` остался версией 2.9.48;
* `bootloader_main.c` (+10 строк) — сохранена запись признаков SBLA/SBLS в SRAM2: upstream 5.0.4 её
  удалил, а прошивка 2.9.48 читает `SRAM2_BASE+5 == 0x29` (`drivers/audio/freedv_uhsdr.c:464`).
  Обычная сборка (без `-DSBLA`/`-DSBLS`) этот блок не компилирует.

Поведенческие отличия 5.0.4 (важно понимать при обновлении):

| Отличие | Смысл |
|---|---|
| `UhsdrBl_JumpToApplication()` | перед переходом в прошивку/DFU отключаются прерывания, `HAL_SuspendTick()`, `HAL_RCC_DeInit()`, чистятся NVIC ICER/ICPR — «чистый» старт прошивки |
| enum вместо магии | `BOOT_CLEARED = 0`, `BOOT_REBOOT = 0x55`, `BOOT_DFU = 0x99`, `BOOT_FIRMWARE = 0x66993300` (`bootloader_main.h:29-35`). Значения `0x55`/`0x99` совместимы с прежним протоколом |
| `__DSB()` перед сбросом | `COMMAND_ResetMCU()`: запись признака в SRAM2 гарантированно доходит до сброса (`command.c:279-289`) |
| `BootFail_Handler(3)` | при невалидной прошивке/цели `BOOT_FIRMWARE`; проверка валидности — `uhsdrBl_IsValidApplication()` (SP в области RAM) |

Совместимость с прошивкой 2.9.48: старые имена и точки входа сохранены, признак SBLA/SBLS пишется,
API прошивки не менялся. **Прошивка версию загрузчика не проверяет** — она только отображает её
(см. §4); совместимость 4.1.2 подтверждена сборкой/кодом, но не полевыми испытаниями.

## 4. Как узнать текущую версию загрузчика

1. Включить трансивер (обычное включение, ничего не удерживая).
2. Открыть меню — кнопка **F1**, затем выбрать группу **System Info** и пункт **Bootloader**
   (`mchf-eclipse/drivers/ui/menu/ui_menu_structure.c:573`).
3. Справа от пункта отображается версия: для этого релиза ожидается `5.0.4` (для старого — `4.1.2`).

Заодно проверьте прошивку: **System Info → Firmware** должно показывать `2.9.48-n96kp3` (v1.2),
а на стартовом экране выводится `UHSDR + Vers. 2.9.48-n96kp3` (`ui_driver.c:6180`).

**Как прошивка это узнаёт.** Обработчик `INFO_BL_VERSION` читает первые 32 КиБ flash с `0x08000000`
и ищет в них ASCII-строку `Version: ` (первые 9 байт); всё, что идёт после неё до NUL, показывается
как версия (`mchf-eclipse/drivers/ui/menu/ui_menu.c:686-718`). Строка компилируется в образ загрузчика
(`VERSION` в `src/bootloader/command.h:57`) — проверено: `Version: 5.0.4` лежит по смещению 27 503,
строки `4.1.2` в образе 5.0.4 нет. Если ничего не найдено, выводятся эвристики для старых
M0NKA-загрузчиков (`M0NKA 0.0.0.9`, `M0NKA 0.0.0.14`) либо `Unknown BL`.

| Показание System Info → Bootloader | Оценка |
|---|---|
| `5.0.4` | PASS — стоит целевой загрузчик |
| `4.1.2` | допустимо — known-good, совместим; обновление не обязательно |
| `Unknown BL` / пусто | FAIL — загрузчик не UHSDR, старый M0NKA или повреждён; разбираться до передач |

## 5. Обновление загрузчика

> **Внимание.** Загрузчик 5.0.4 **не прошивался и на железе не испытывался**. Обновляйте только при
> необходимости (например, для перехода на upstream-совместимый API) и только при наличии ST-Link
> и файла `bl-mchf-4.1.2-known-good.bin`. При неудачной записи первые 32 КиБ могут остаться
> стёртыми: устройство не запустится, `BAND+`/`BAND−` не сработают (кнопки обрабатывает сам загрузчик).
> Восстановление — только SWD (ST-Link) или перевод BOOT0 в режим загрузки из system memory
> (аппаратно, если плата это позволяет). Это и есть риск «кирпича».

Требования: стабильное питание, заряд/БП с запасом по току, **не отключать питание** во время
записи; перед записью сверить SHA-256 выбранного файла с `release/v1.2/SHA256SUMS.txt`.

### 5.1. Вариант A — SWD/ST-Link (рекомендуется)

```powershell
# STM32CubeProgrammer CLI (Windows), файл из release/v1.2
STM32_Programmer_CLI.exe -c port=SWD -w bl-mchf-5.0.4.bin 0x08000000 -v -rst
```

1. Подключить ST-Link к SWD-разъёму платы, проверить связь (`-c port=SWD` без ошибок).
2. Записать `bl-mchf-5.0.4.bin` по адресу `0x08000000`, включить verify (`-v`).
3. Дождаться успешной верификации, снять питание/перезапустить (`-rst`).
4. Проверить: устройство стартует, **System Info → Bootloader = 5.0.4** (§4).
5. Сразу провести стендовый smoke-тест (см. §9, таблица проверок) — до этого загрузчик считается
   кандидатом, а не проверенным.

### 5.2. Вариант B — ROM-DFU STM32 (BAND+ при включении)

Пользуйтесь, если SWD недоступен, но загрузчик ещё жив (он обрабатывает `BAND+`).

1. Выключить трансивер.
2. Нажать и **удерживать BAND+**, включить питание. На экране появится экран DFU загрузчика
   (тексты из `src/bootloader/bootloader_main.c:43-55`): `DFU Update Mode`,
   `Keep Power pressed until finish.`, `Release Band+ to start DFU Mode.`,
   `Screen may go white. This is ok.`, `PC should recognize new USB device.`
3. **Отпустить BAND+** — загрузчик запишет признак `BOOT_DFU` в SRAM2 и перезагрузится; на старте
   `Bootloader_CheckAndGoForBootTarget()` увидит признак, сделает `__HAL_REMAPMEMORY_SYSTEMFLASH()`
   и перейдёт на `0x00000000` — в ROM-загрузчик STM32 (`bootloader_main.c:397-428`).
4. Подключить USB-кабель к ПК: в диспетчере устройств появится `STM32 BOOTLOADER` (DFU).
5. Прошить загрузчик по адресу `0x08000000`:

```powershell
STM32_Programmer_CLI.exe -c port=USB1 -w bl-mchf-5.0.4.bin 0x08000000 -v -rst
# альтернатива при наличии dfu-util:
dfu-util -a 0 -s 0x08000000:leave -D bl-mchf-5.0.4.bin
```

6. После сброса проверить §4 и выполнить стендовый smoke-тест (§9).

**Почему этот путь работает только с живым загрузчиком.** `BAND+` опрашивается кодом UHSDR-загрузчика;
в ROM-DFU устройство уходит уже из него. Если загрузчик стёрт/повреждён, удерживание BAND+ ничего
не даст — нужен SWD или BOOT0.

### 5.3. Откат загрузчика

Откат выполняется **тем же способом**, что и обновление, файлом
`release/v1.2/bl-mchf-4.1.2-known-good.bin` (31 496 Б, SHA-256
`933249535DD5CACB871708802C4D09549AB84E2D4DA7AE53A69BB6E2FF3B8CA1`) по адресу `0x08000000`.
После отката **System Info → Bootloader** должен показывать `4.1.2`; прошивка 2.9.48 с ним работает.

## 6. Обновление прошивки через загрузчик (не загрузчика!)

**Важно:** загрузчик читает USB-флешку как **USB-хост** (в его сборке `usb_host.c`, `usbh_msc.c`,
FatFs; на экране `USB Drive Mode` / `USB Drive detected.`). То есть флешка вставляется
**в трансивер**, а не трансивер подключается к ПК как диск. `docs/BUILD.md` §5.1 описывает этот
режим так же («флешка вставляется в трансивер, на ПК диск не появляется») — документы согласованы.

1. Подготовить USB-флешку с FAT и положить в **корень** файл `fw-mchf.bin` из пакета
   (GCC9 default: **312 216 Б**, Build `Nov 27 2026 - 14:55:12`; SHA-256 — из SHA256SUMS.txt пакета.
   v1.2 GCC15: 321 392 Б, SHA-256 `FD5D…951A` — историческая, **не прошивать**: зависает).
   Имя файла фиксировано: `BASE_FILE = fw-` + `TRX_ID` = `fw-mchf` (`command.h:50-56`).
   Перед копированием проверьте SHA-256 на ПК: **загрузчик не проверяет CRC/подпись**, только размер
   (≤ 960 КиБ) и результат записи во flash (`command.c:231-274`).
2. Выключить трансивер, нажать и удерживать **BAND−**, включить питание. Появится экран загрузчика:
   `<TRX_NAME> Bootloader` (в CLI-сборке `mcHF QRP Bootloader`), `Firmware Name: fw-mchf`,
   `USB Drive Mode`, `Release Band- to skip firmware update`.
3. Вставить флешку в USB-порт трансивера. После определения: `USB Drive detected.`; загрузчик
   **всегда** сначала сохраняет текущую прошивку: `Saving Flash to "fw-mchf.old"...`
   (дамп области прошивки 960 КиБ, т.е. 983 040 Б), затем, если **BAND− всё ещё удерживается**,
   пишет новую: `Updating firmware using "fw-mchf.bin"...`. Если отпустить BAND− до определения
   флешки — будет только дамп, `Skipping firmware update.` (кнопка и есть подтверждение обновления).
4. Дождаться `Finished.`, затем `Remove drive or press Band- to reboot.` / `Press Power to switch off.`
5. Вынуть флешку, перезагрузиться, проверить версию: стартовый экран / **System Info → Firmware** =
   `2.9.48-n96kp3`, **Build** = дата из README пакета (GCC9 default — `Nov 27 2026 - 14:55:12`),
   **Bootloader** не изменился (обновлялась только прошивка). **Если после splash интерфейс завис**
   (оба LED) — это прошивка, собранная GCC 15.2.1, а не загрузчик: откатитесь на GCC9-сборку
   (docs/BUILD.md §1.1, docs/CHECKLIST.md).

Примечания:

* стираются и пишутся секторы начиная с `0x08010000`; загрузчик и конфигурация (0x08008000–0x0800FFFF)
  не затрагиваются, поэтому настройки обычно сохраняются. Но **раскладка EEPROM между сборками UHSDR
  различается** — после смены прошивки проверьте меню. Загрузка дефолтов при необходимости: удерживать
  **F1+F3+F5** при включении, подтвердить **BAND+ и BAND−**, настройки сохранятся при выключении питания
  (`ui_driver.c:5476-5580`; подробнее — docs/SAFETY.md §1);
* предупреждение `Firmware change detected! Please review settings!` (`ui_driver.c:6224-6231`)
  срабатывает только при смене **числовой** версии (major/minor/release). v1.1 → v1.2 меняет только
  суффикс продукта (`n96kp2`→`n96kp3`), числовая версия 2.9.48 не меняется — предупреждения не будет;
* **откат прошивки:** переименовать на флешке `fw-mchf.old` в `fw-mchf.bin` (это полный дамп области
  прошивки) и повторить обновление; либо прошить предыдущий релиз через DFU (§8).

## 7. Если что-то пошло не так

### 7.1. BootFail_Handler — подсветка мигает, экран тёмный

Загрузчик не смог запустить прошивку (`uhsdrBl_IsValidApplication()` не подтвердил вектор) и ушёл в
`BootFail_Handler()` (`command.c:108-125`): подсветка выключается, затем **мигает сериями по 2**
(`BootFail_Handler(2)` — невалидная прошивка) или **по 3** (путь `BOOT_FIRMWARE`, в текущей прошивке
не используется). Экран при этом не инициализирован. Что делать:

1. Нажать **POWER** — обработчик ошибки позволяет выключиться (`Wait()` проверяет кнопку питания).
2. Включить с удержанием **BAND−** и повторить обновление прошивки с флешки (§6) — загрузчик жив.
3. Если USB-путь недоступен — включить с **BAND+** и прошить `fw-mchf.hex` через ROM-DFU (§8).

### 7.2. FlashFail_Handler — «Error Code N» и мигание красного LED

Ошибка USB/FatFs/flash при обновлении (`command.c:57-104`). На экране: `Error Code  N` (два пробела — как в коде, `command.c:76`) и текст, красный LED мигает N раз. Кнопка POWER выключает устройство.

| Код | Текст загрузчика | Вероятная причина / действие |
|---|---|---|
| 1 | USB problem | флешка/кабель/порт; переподключить, попробовать другую FAT-флешку |
| 2 | `fw-mchf.bin` not found | файла нет в корне или неверное имя; проверить регистр/имя |
| 3 | Flash memory too small | файл больше 960 КиБ (не прошивка или повреждён) |
| 4 | Problem writing `fw-mchf.old` | флешка защищена/полна/сбойная; заменить |
| 5 | `Problem readingfw-mchf.bin` — в прошивке пробел между `reading` и именем файла потерян (`command.c:64`) | чтение файла; перезаписать файл, проверить SHA-256 |
| 6 | Flash programming problem | сбой записи flash; повторить, при повторе — DFU/SWD |
| 7 | Flash erase problem | то же; питание/плата |
| 8 | Flash write protected | включена защита flash (RDP); требует программатора |

### 7.3. Устройство не включается, BAND+ не реагирует

Признак повреждённого/стёртого загрузчика (или аппаратной проблемы). `BAND+`/`BAND−` обрабатывает
код загрузчика, поэтому этот путь уже недоступен. Восстановление:

1. SWD/ST-Link: записать `bl-mchf-5.0.4.bin` (или `bl-mchf-4.1.2-known-good.bin`) по `0x08000000`,
   затем прошить прошивку (`fw-mchf.bin` по `0x08010000` или `fw-mchf.hex`).
2. Если SWD недоступен — перевести BOOT0 в состояние загрузки из system memory (аппаратно) и
   использовать ROM-DFU (`STM32_Programmer_CLI -c port=USB1 …`).

## 8. DFU-путь для восстановления прошивки

Используется, когда обновление с флешки не удалось, прошивка не стартует, но загрузчик жив
(или есть ST-Link). ROM-DFU — это загрузчик STM32 в system memory; UHSDR-загрузчик только
переводит в него устройство по `BAND+`.

1. Выключить, удерживая **BAND+**, включить питание → экран `DFU Update Mode`.
2. Отпустить BAND+ → ПК увидит `STM32 BOOTLOADER`.
3. Прошить один из вариантов:

```powershell
# прошивка: .hex содержит адреса сам, .bin нужно писать по 0x08010000
STM32_Programmer_CLI.exe -c port=USB1 -w fw-mchf.hex -v -rst
STM32_Programmer_CLI.exe -c port=USB1 -w fw-mchf.bin 0x08010000 -v -rst
# загрузчик: всегда по 0x08000000
STM32_Programmer_CLI.exe -c port=USB1 -w bl-mchf-5.0.4.bin 0x08000000 -v -rst
```

4. После сброса проверить **System Info → Firmware/Bootloader** (§4) и настройки.

## 10. Ограничения и правила

* 5.0.4 **не прошивался и не испытывался**; проверены только сборка, линковка, карта памяти, строка
  версии и совместимость по коду. USB-хост/DFU/экран проверены статически (P2-1, p2-bootloader).
* Свободного места **1 148 Б**; любые добавления в загрузчик требуют пересборки и контроля размера.
* Не меняйте `UHSDR_BOOT_VERS` без пересборки обоих артефактов и проверки совместимости.
* Не отключайте питание во время записи. Не прошивайте загрузчик «на всякий случай» — только по
  необходимости и с бэкапом/программатором.
* Не полагайтесь на файл `.old` как на единственный бэкап: он лежит на той же флешке и легко теряется.
* `docs/BUILD.md` §5.1 и этот документ согласованы: загрузчик — USB-хост, флешка вставляется
  в трансивер; на ПК трансивер диском не появляется.
