# Сборка прошивки UHSDR / RS-918 из командной строки

В этом репозитории лежит прошивка **UHSDR 2.9.48** (форк Nizar 3V8MN) для SDR-трансиверов
mcHF / RS-918. Ниже — как собрать `fw-mchf` (прошивку) и `bl-mchf` (загрузчик) **без Eclipse,
без EmBitz и без GNU make**, одной командой.

Сборка полностью повторяет то, что делает `mchf-eclipse/Makefile` для `BUILDFOR=F4`
(STM32F407, 1 МБ flash / 128 КБ RAM + 64 КБ CCM), но список исходников и флаги берутся из тех
же самых `*.mak`-файлов, поэтому набор файлов и опции не расходятся с оригиналом.

> ⚠️ **Тулчейн: только GCC 9.3.1.** Прошивки, собранные GCC 10+/15.2.1, стартуют, показывают
> splash и кратковременно UI, после чего **зависают** на RS-918 (оба светодиода). Сборка, релизы и
> пакеты — только `xPack GNU Arm Embedded GCC 9.3.1` (см. §1.1). Прежние v1.0–v1.2 собраны
> GCC 15.2.1 и для железа **непригодны**.

## 1. Что нужно установить

| Компонент | Требование | Пример в этой системе |
|---|---|---|
| Python | 3.8+ (стандартная библиотека, никаких пакетов ставить не нужно) | Python 3.12 |
| ARM toolchain | `arm-none-eabi-gcc` / `g++` / `objcopy` / `size` / `nm` — **xPack GNU Arm Embedded GCC 9.3.1 (обязателен)**; GCC 10+/15.2.1 для прошивки непригоден (§1.1) | `E:\tools\gcc9\xpack-arm-none-eabi-gcc-9.3.1-1.3\bin` |
| Git | только для работы с репозиторием, для сборки не нужен | — |
| make / Eclipse / EmBitz | **не нужны** | — |

Тулчейн **не обязан быть в `PATH`**: `tools/build.py` ищет его в таком порядке

1. `--toolchain <папка_с_arm-none-eabi-gcc>`
2. переменная окружения `ARM_GCC_BIN`
3. `E:\tools\gcc9\xpack-arm-none-eabi-gcc-9.3.1-1.3\bin` — **GCC 9.3.1, значение по умолчанию**
4. `E:\tools\gcc-arm\bin` — fallback (современный GCC; `build.py` печатает предупреждение)
5. `PATH`

### 1.1. Toolchain: GCC 9.3.1 обязателен (GCC 15.2.1 не годится)

**Симптом.** Прошивка, собранная xPack GNU Arm Embedded GCC **15.2.1** (наш прежний CI-тулчейн),
стартует, показывает splash и кратковременно интерфейс, после чего **зависает** — горят оба
светодиода. На железе пользователя это воспроизведено; та же исходная версия, собранная **GCC 9.3.1**,
работает нормально (System Info: Firmware `2.9.48-n96kp3`, Build `Nov 27 2026 - 14:55:12`,
Bootloader `5.0.4`).

**Причина.** Разница компилятора/LTO: UB в коде Nizar, который GCC 9.3.1 «терпит», на GCC 15.2.1
приводит к зависанию. Поэтому **GCC 9.3.1 — обязательное требование** для любых артефактов,
предназначенных для железа; правка UB — отдельная будущая задача.

**Что зафиксировано:**

- автодетект `tools/build.py` (порядок выше): без ключей берётся GCC 9.3.1 из
  `E:\tools\gcc9\xpack-arm-none-eabi-gcc-9.3.1-1.3\bin`; если найденный компилятор — не GCC 9.x,
  печатается предупреждение о зависании GCC 15.x;
- `--toolchain DIR` и `$ARM_GCC_BIN` по-прежнему переопределяют автодетект (используются в Docker);
- Dockerfile/CI закреплены на `xPack GNU Arm Embedded GCC 9.3.1-1.3` (SHA256 архива
  `4845d261b000d921887fc801427542eed2df1616f63a2969a2640f8be2593686`) — см. [CI.md](CI.md);
- все релизы **v1.0–v1.2 и прежний пакет bench-2026-11-27 собраны GCC 15.2.1 и невалидны** для
  железа; актуальный пакет — `release/bench-2026-11-27` (GCC 9.3.1).

Проверить тулчейн:

```powershell
E:\tools\gcc9\xpack-arm-none-eabi-gcc-9.3.1-1.3\bin\arm-none-eabi-gcc --version
# arm-none-eabi-gcc.exe (xPack GNU Arm Embedded GCC, 64-bit) 9.3.1 20200408 (release)
```

Если тулчейн лежит в другом месте:

```powershell

# или
$env:ARM_GCC_BIN = "C:\Program Files\ArmGNUToolchain\bin"
```

## 2. Сборка (одна команда)

Все команды выполняются **из корня репозитория** (`RS918_Nizar96K_Pro`, там, где лежит папка
`mchf-eclipse`). Скрипт можно запускать и из любого другого каталога — пути он определяет
относительно своего расположения.

```powershell
cd "E:\harnet\sdr 11\RS918_Nizar96K_Pro"

python tools\build.py all          # прошивка + загрузчик  (то, что нужно обычно)
python tools\build.py firmware     # только fw-mchf
python tools\build.py bootloader   # только bl-mchf
python tools\build.py clean        # удалить каталог build\ целиком
```

Полезные ключи:

| Ключ | Смысл |
|---|---|
| `-j N`, `--jobs N` | число параллельных компиляций (по умолчанию — число ядер CPU) |
| `-f`, `--force` | полная пересборка (игнорировать уже собранные объектные файлы) |
| `-v`, `--verbose` | печатать каждую команду компиляции |
| `-t DIR`, `--toolchain DIR` | каталог с `arm-none-eabi-gcc` |
| `--build-dir DIR` | каталог артефактов (по умолчанию `<repo>\build`) |

Код возврата: **0** — успех, **2** — ошибка сборки (в конце печатается команда и вывод
компилятора/линкера), **130** — прерывание с клавиатуры.

Сборка «с нуля» на 12 логических ядрах занимает ~30 секунд (528 объектных файлов прошивки +
116 загрузчика; компиляция — ~13 с и ~4 с, остальное — LTO-линковка и `objcopy`),
инкрементальная — ~12 секунд: после правки одного заголовка перекомпилируются только зависящие
от него файлы (учёт заголовков в `*.d` исправлен, см. §4).

**Проверки после сборки.** Host-тесты (ЦОС-таблицы, `files.mak`, карта EEPROM, версия/идентификация):
`python tests\run_all.py` — после B1 **1754 проверки, 0 failed, 3 known** (в v1.2 было 1134); CI/Docker с pinned
toolchain и контроль бюджета артефактов — [docs/CI.md](CI.md).

**Сборка с FreeDV (opt-in, B4).** Отдельная прошивка с FreeDV без изменения default-конфигурации:

```powershell
python tools\build.py all --freedv --build-dir build-freedv --force -j 8
```

Флаг добавляет `-DN96K_FREEDV` только прошивке (загрузчик не меняется): fw **555 608 Б**,
RAM static **48 552**, CCM 63 972 (свободно 1 564), предупреждений 50 (GCC 9.3.1). Default-сборка
без флага остаётся продуктовой (**312 216 Б**, 50 предупреждений в all-сборке). Размеры, бюджет,
ограничения и план стенда — [docs/FREEDV.md](FREEDV.md).

**Полная сборка (opt-in, B6).** Для стенда — вариант без Nizar-ограничения `IS_SMALL_BUILD`
(включает FreeDV автоматически и const-окна Ханна 512/1024):

```powershell
python tools\build.py all --full --build-dir build-full --force -j 8
```

Флаг добавляет прошивке `-DN96K_FULL_BUILD` и `-DN96K_FREEDV` (вторая конфигурация памяти
обязательна — иначе `sizeof(struct freedv)` растёт на ~10,9 КБ heap и расчётный запас стека
отрицательный); загрузчик не меняется, default-сборка без флагов не меняется. Полная сборка: fw
**561 720 Б**, RAM static **48 552**, CCM **63 972** (97,6 %, свободно 1 564), 50 предупреждений
(GCC 9.3.1; Build `Nov 27 2026 - 15:05:12`).
Это **стендовая** конфигурация, не продукт: FreeDV на железе не проверен, heap/стек на границе,
CCM почти заполнена, EEPROM-индексы DIGI-режимов между сборками различаются — подробно
[docs/STATUS.md](STATUS.md) и `_audit/dev/nizar-full.md`.

**Уровень оптимизации (B5).** Default — `-O2`; для экспериментов можно собрать `-O3` (сильно больше
flash, CPU-эффект проверяется на стенде) или `-Os` (для размера; в текущем дереве **не линкуется**
из-за C99-inline в заголовках):

```powershell
python tools\build.py all --opt-level O3 --build-dir build-o3 --force -j 8
python tools\build.py all --freedv --opt-level O3 --build-dir build-o3-freedv --force -j 8
```

Замеры (F4, GCC 9.3.1): `-O2` fw **312 216 Б** (default, B6; Build `Nov 27 2026 - 14:55:12`);
`-O3` fw **412 536 Б**, RAM **42 436**, CCM 63 476 (Build `Nov 27 2026 - 15:06:17`; загрузчик всегда
`-Os`, не меняется). Host-тесты и бюджет проверены; выбор уровня — осознанно, default оставлен
`-O2`. Для стенда собран пакет release/bench-2026-11-27 (default/FreeDV/full/O3 + printable).

по определению; совпадение при повторной линковке без изменения исходников — см. §7.

## 4. Как это устроено (и чем отличается от `make`)

`tools/build.py` — маленький драйвер сборки на Python:

1. парсит `mchf-eclipse/include.mak`, `files.mak`, `bootloader.mak`, `f4-include.mak`,
   `f4-files.mak`, `f4-bootloader.mak` (переменные `SUBDIRS`, `HAL_SUBDIRS`, `SRC`, `HAL_SRC`,
   `DSPLIB_SRC`, `BL_SRC`, `BL_HAL_SRC`);
2. компилирует каждый файл теми же флагами, что и Makefile:
   - общие: `-mcpu=cortex-m4 -mfloat-abi=hard -mfpu=fpv4-sp-d16 -mthumb -DARM_MATH_CM4
     -DCORTEX_M4 -DSTM32F407xx -D__FPU_PRESENT=1U -DUSE_HAL_DRIVER -DDEBUG -DUSE_FULL_ASSERT
     -DTRACE -D_GNU_SOURCE -DTRX_ID="mchf" -DTRX_NAME="mcHF QRP" -ffunction-sections
     -fdata-sections -flto -Wall -Wno-unused-function -g3`;
   - прошивка: `-O2`;  загрузчик: `-Os -DBOOTLOADER_BUILD`;
   - все `-I` из `SUBDIRS` + `HAL_SUBDIRS`, `-std=gnu11` (C) / `-std=gnu++11` (C++);
3. линкует `g++` с `-flto --specs=nano.specs -g3 -Xlinker --gc-sections` и скриптом
   `linker/arm-gcc-link_f4_flash1024k.ld` (прошивка) или
   `linker/arm-gcc-link-bootloader_f4.ld` (загрузчик), библиотеки `-lm -lc -lnosys`;
4. делает `.bin`/`.hex` через `objcopy` и печатает расход flash/RAM.

Отличия от `make all` (осознанные, ничего не меняют в коде прошивки):

* целевые объекты строятся в `build/`, а не рядом с исходниками;
* `g++` при линковке получает список объектных файлов через response-файл `@build\firmware.link.rsp`
  (в Windows командная строка ограничена 32 767 символами, 528 путей туда не влезают) —
  результат линковки идентичен;
* добавлен `-fcommon` (совместимость с GCC ≥ 10, иначе LTO-линковка падает с
  `multiple definition of bm_set_normal / USBD_COMP_CfgDesc`);
* добавлены `-MMD -MP` — только для корректной инкрементальной сборки (файлы `.d`).
  Разбор `.d` в `tools/build.py` исправлен: зависимости — это Windows-пути с буквой диска
  (`E:\…`) и экранированными пробелами, а gcc/ld при `-MP` дописывает в конец файла phony-цели;
  прежний разбор «по первому двоеточию» молча терял все заголовки (правка только в драйвере,
  флаги не менялись);
* `-DTRX_NAME="mcHF QRP"` — без одинарных кавычек. Makefile задаёт `TRX_NAME='mcHF QRP'`,
  и после подстановки в строку получается `'mcHF QRP'` **вместе с кавычками** (они видны в
  строке версии); здесь строка чистая;
* не генерируются `.dfu` (скрипт `support/hex2dfu/hex2dfu.py` требует Python 2 и модуль
  `intelhex`) и handbook (`support/ui/menu/mk-menu-handbook`, bash) — для прошивки они не нужны.

### 4.1. Правки исходников для современных GCC (10+/15.2.1) / binutils 2.45 (P0-2)

Проект 2018 года; на современном тулчейне он не собирался. Правки минимальные — **только типы,
прототипы и ассемблерные директивы; логика Nizar и P0-патчи не тронуты** (полный разбор — `_audit/dev/p-build.md`). Правки сделаны при переходе на GCC 15.2.1; на **GCC 9.3.1 они не требуются**, но безвредны и оставлены (нужны для проверочных сборок современным GCC). **Продуктовые артефакты — только GCC 9.3.1** (§1.1):

| Файл | Правка | Почему |
|---|---|---|
| `mchf-eclipse/files.mak` | + `iir_2_8k.c`, + `iir_16k5_96ks.c` (46 из 46 фильтров) | символы использовались, но файлы не компилировались — `undefined reference` |

## 5. Как прошивать

### 5.1 Прошивка (firmware) — через USB-накопитель и загрузчик, без программатора

Загрузчик UHSDR 5.0.4 работает как **USB-хост**: он читает файл `fw-mchf.bin` из корня
**USB-флешки, вставленной в разъём трансивера** (`usb_host.c`/`usbh_msc.c` + FatFs; экраны
`USB Drive Mode` / `USB Drive detected.`). На компьютере трансивер диском **не** появляется.

1. Подготовить USB-флешку с FAT/FAT32 и положить в **корень** `fw-mchf.bin` из релиза
   (`release/vX/`) или из `build/`.
2. Выключить трансивер, нажать и **удерживать** **BAND−**, включить питание. На экране —
   `mcHF QRP Bootloader`, `Firmware Name: fw-mchf`, `USB Drive Mode`,
   `Release Band- to skip firmware update`.
3. Вставить флешку в USB-порт трансивера. Загрузчик обнаружит её (`USB Drive detected.`),
   сохранит текущую прошивку в `fw-mchf.old` (дамп 983 040 Б) и, пока **BAND− удерживается**,
   запишет `fw-mchf.bin` (`Updating firmware using "fw-mchf.bin"...`).
   Если отпустить BAND− до обнаружения флешки — будет только дамп (`Skipping firmware update.`),
   прошивка не меняется.
4. После появления строки `Updating firmware using "fw-mchf.bin"...` кнопку BAND− можно отпустить.
   Дождаться `Finished.` и `Remove drive or press Band- to reboot.`; **не выключать питание**
   до `Finished.`.
5. Извлечь флешку (или нажать BAND− для перезагрузки). Проверить: **System Info → Firmware** =
   `2.9.48-n96kp3`, **Bootloader** = `5.0.4`, **Build** = дата из README пакета (для default
   bench-2026-11-27 — `Nov 27 2026 - 14:55:12`). Интерфейс должен работать без зависания: если
   после splash он замирает (оба LED) — прошивка собрана не GCC 9.3.1, откатитесь (§1.1).
   На флешке останется `fw-mchf.old` — бэкап прежней прошивки.
6. **Откат прошивки:** переименовать `fw-mchf.old` → `fw-mchf.bin` на флешке и повторить пункты 2–5.

Если на вашем экземпляре нет работающего USB-хоста/флешки — используйте DFU (см. §5.2 и
`docs/TESTPLAN.md` §3.3).

### 5.2 Загрузчик (bootloader) — только программатором

Собранный загрузчик — **UHSDR bootloader 5.0.4** (`UHSDR_BOOT_VERS` в `src/uhsdr_version.h`,
исходники — upstream UHSDR 2.12.2). Сам загрузчик строку версии на экран не печатает (экран
обновления: `mcHF QRP Bootloader`, `Firmware Name: fw-mchf`, `USB Drive Mode`); версия видна из
прошивки — **System Info → Bootloader** = `5.0.4` (`ui_menu.c:686-718`; см. docs/BOOTLOADER.md §4).
Образ 5.0.4: в релизах/пакете — **31 620 из 32 768 байт** (GCC 15.2.1, запас 1 148 — известная
рабочая версия, прошивать только при необходимости); при полной CLI-сборке на **GCC 9.3.1**
загрузчик собирается **32 416 из 32 768** (запас 352; это CI/all-сборка, в пакет не входит). Отличия от прежнего
4.1.2 (2.9.48): переход в прошивку/DFU выполняется через `UhsdrBl_JumpToApplication()` (отключение
прерываний, `HAL_RCC_DeInit()`, сброс NVIC — надёжнее старт прошивки), состояния перезагрузки
заданы enum `BOOT_REBOOT`/`BOOT_DFU`/`BOOT_FIRMWARE`, перед сбросом MCU добавлен `__DSB()`.
Совместимость с прошивкой 2.9.48 сохранена: старые точки входа (`bootloader_main`,
`BL_Application`, `mchfBl_CheckAndGoForDfuBoot`) — псевдонимы в `bootloader_main.h`, а признак
SBLA/SBLS в SRAM2 (его читает `drivers/audio/freedv_uhsdr.c`) по-прежнему выставляется.
Загрузчик 4.1.2 (2.9.48) тоже работает с этой прошивкой; менять его нужно только если он старее.

Загрузчик занимает первые 32 КиБ flash (`0x08000000`), поэтому обновляется либо по SWD, либо
через встроенный DFU STM32.

**Вариант A — ST-Link / SWD (рекомендуется):**

```powershell
# любым из инструментов, например STM32CubeProgrammer (GUI/CLI) или openocd:
STM32_Programmer_CLI.exe -c port=SWD -w build\bl-mchf.bin 0x08000000 -v -rst
```

**Вариант B — DFU (встроенный загрузчик STM32):**

1. Нажать и удерживать **BAND+**, включить питание → на экране `DFU`.
   Загрузчик установит признак и перезагрузится в системный DFU STM32
   (`Bootloader_CheckAndGoForBootTarget`, старое имя `mchfBl_CheckAndGoForDfuBoot`;
   после `__HAL_REMAPMEMORY_SYSTEMFLASH()` переход на адрес `0x00000000`).
2. На компьютере появится устройство `STM32 BOOTLOADER` (DFU). Залить `build\bl-mchf.bin`
   по адресу `0x08000000` (STM32CubeProgrammer: `-c port=USB1 -w build\bl-mchf.bin 0x08000000 -v -rst`).
   Для DfuSe нужен `.dfu` — этот скрипт его не делает (см. §4), используйте CubeProgrammer или `.hex`.

**Важно:** не отключайте питание во время записи загрузчика. Восстановить повреждённый загрузчик
комбинацией кнопок **нельзя**: `BAND+`/`BAND−` обрабатывает сам загрузчик. При неудачной записи
трансивер не стартует; восстановление — только через **SWD (ST-Link)** или **BOOT0 → ROM-DFU STM32**
(STM32CubeProgrammer). Поэтому обновляйте загрузчик только имея под рукой ST-Link.

| Симптом | Что делать |

| `link failed for fw-mchf.elf` | то же; частые причины — забытый исходник в `*.mak` или дубликат глобального символа в заголовке |
| предупреждения | все они пишутся в `build\warnings.log`; эталон **GCC 9.3.1** — **50 строк** в all-сборке (fw 46 + bl 4), 16 различных текстов = baseline warning-гейта (лимит 50); все — существующие в коде Nizar/upstream, ни одного на строках product-патчей. Исторические GCC15-сборки v1.0–v1.2 давали 78–80 строк (невалидны, §1.1); разбор — `_audit/dev/p-build.md` |
| непонятно, что собралось | `build\build-summary.json` (размеры), `build\fw-mchf.map` (карта), `build\compile_commands.json` |
| хочется повторить «как в Eclipse» | `python tools\build.py all --force -v` |

отладочной информацией) и ~1,5 ГБ RAM при `-j12`.

## 7. Ограничения

* `.dfu` не собирается (нужен Python 2 + `intelhex`); `.hex` собирается — его достаточно для
  STM32CubeProgrammer.
* Handbook/меню-граф (`make ...handbook`) не генерируются.
* Прошивка собирается **только под F4** (RS-918/mcHF): скрипт читает `f4-*.mak` и
  F4-скрипты линковки. В дереве при этом **остались** каталоги других платформ upstream
  (`basesw/ovi40` — F7, `basesw/ovi40-h7` — H7), их `f7-*.mak`/`h7-*.mak`, скрипты линковки
  F7/H7 и Eclipse-конфигурации OVI40 (`.cproject`). Они не удалялись, но этим продуктом не
  поддерживаются, не собираются и не проверялись; `Makefile` формально сохраняет ветки
  `BUILDFOR=F7/H7` (без `$(error)`). Чистка дерева от них — отдельная задача (P2).
* CCM-память занята на 96,9 % (default: 63 476 из 65 536 байт, свободно 2 060; в v1.2 не выросла);
  в opt-in FreeDV/full-сборках — 63 972 (свободно 1 564). При добавлении буферов в CCM сборка
  упадёт на линковке; свободная RAM (128 КиБ) при этом ещё есть.
* Байт-в-байт воспроизводимость между полными пересборками не гарантируется: в прошивку
  зашивается `fwt-<__DATE__ __TIME__>` (`UHSDR_BUILD_DAT`). Проверено: две полные сборки
  подряд дают одинаковые размеры и **идентичную карту памяти**, `bl-mchf.bin` совпадает
  побайтно, а `fw-mchf.bin` отличается только 2–4 байтами времени сборки (см. §3).
* **GCC 15.2.1 не годится для прошивок** (зависание после splash на железе): успешная сборка и
  host-тесты не гарантируют работоспособность; используйте GCC 9.3.1 (§1.1).
* Сборка проверена на Windows + xPack GNU Arm Embedded GCC **9.3.1** + Python 3.12;
  Linux/macOS локально не проверялись (скрипт написан кроссплатформенно, но пути и response-файлы
  рассчитаны на Windows); Linux-сборка — в Docker/CI (GCC 9.3.1-1.3, см. docs/CI.md).
* В `warnings.log` остаются предупреждения компилятора/линковки (см. §3/§4.1 и
  `_audit/dev/p-build.md`); `-Werror` не включался, чтобы не менять поведение Nizar.
