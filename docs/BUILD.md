# Сборка прошивки UHSDR / RS-918 из командной строки

В этом репозитории лежит прошивка **UHSDR 2.9.48** (форк Nizar 3V8MN) для SDR-трансиверов
mcHF / RS-918. Ниже — как собрать `fw-mchf` (прошивку) и `bl-mchf` (загрузчик) **без Eclipse,
без EmBitz и без GNU make**, одной командой.

Сборка полностью повторяет то, что делает `mchf-eclipse/Makefile` для `BUILDFOR=F4`
(STM32F407, 1 МБ flash / 128 КБ RAM + 64 КБ CCM), но список исходников и флаги берутся из тех
же самых `*.mak`-файлов, поэтому набор файлов и опции не расходятся с оригиналом.

## 1. Что нужно установить

| Компонент | Требование | Пример в этой системе |
|---|---|---|
| Python | 3.8+ (стандартная библиотека, никаких пакетов ставить не нужно) | Python 3.12 |
| ARM toolchain | `arm-none-eabi-gcc` / `g++` / `objcopy` / `size` / `nm` — xPack GNU Arm Embedded GCC **15.2.1** (проверено), подойдёт и 10–14 | `E:\tools\gcc-arm\bin` |
| Git | только для работы с репозиторием, для сборки не нужен | — |
| make / Eclipse / EmBitz | **не нужны** | — |

Тулчейн **не обязан быть в `PATH`**: `tools/build.py` ищет его в таком порядке

1. `--toolchain <папка_с_arm-none-eabi-gcc>`
2. переменная окружения `ARM_GCC_BIN`
3. `E:\tools\gcc-arm\bin` (значение по умолчанию для этого проекта)
4. `PATH`

Проверить тулчейн:

```powershell
E:\tools\gcc-arm\bin\arm-none-eabi-gcc --version
# arm-none-eabi-gcc.exe (xPack GNU Arm Embedded GCC x86_64) 15.2.1 20251203
```

Если тулчейн лежит в другом месте:

```powershell
python tools\build.py all --toolchain "C:\Program Files\ArmGNUToolchain\bin"
# или
$env:ARM_GCC_BIN = "C:\Program Files\ArmGNUToolchain\bin"
```

## 2. Сборка (одна команда)

Все команды выполняются **из корня репозитория** (`RS918_Nizar96K_Pro`, там, где лежит папка
`mchf-eclipse`). Скрипт можно запускать и из любого другого каталога — пути он определяет
относительно своего расположения.

```powershell
cd "E:\harnet\sdr 11\RS918_Nizar96K_Pro"

python tools\build.py all          # прошивка + загрузчик  (то, что нужно обычно)
python tools\build.py firmware     # только fw-mchf
python tools\build.py bootloader   # только bl-mchf
python tools\build.py clean        # удалить каталог build\ целиком
```

Полезные ключи:

| Ключ | Смысл |
|---|---|
| `-j N`, `--jobs N` | число параллельных компиляций (по умолчанию — число ядер CPU) |
| `-f`, `--force` | полная пересборка (игнорировать уже собранные объектные файлы) |
| `-v`, `--verbose` | печатать каждую команду компиляции |
| `-t DIR`, `--toolchain DIR` | каталог с `arm-none-eabi-gcc` |
| `--build-dir DIR` | каталог артефактов (по умолчанию `<repo>\build`) |

Код возврата: **0** — успех, **2** — ошибка сборки (в конце печатается команда и вывод
компилятора/линкера), **130** — прерывание с клавиатуры.

Сборка «с нуля» на 12 логических ядрах занимает ~30 секунд (528 объектных файлов прошивки +
116 загрузчика; компиляция — ~13 с и ~4 с, остальное — LTO-линковка и `objcopy`),
инкрементальная — ~12 секунд: после правки одного заголовка перекомпилируются только зависящие
от него файлы (учёт заголовков в `*.d` исправлен, см. §4).

**Проверки после сборки.** Host-тесты (ЦОС-таблицы, `files.mak`, карта EEPROM, версия/идентификация):
`python tests\run_all.py` — в v1.2 **1134 проверки, 0 failed, 3 known**; CI/Docker с pinned
toolchain и контроль бюджета артефактов — [docs/CI.md](CI.md).

и затем `... all --force`) дали одинаковые размеры `.bin`/`.elf`/`.hex`/`.map`, одинаковые
секции и **идентичную карту памяти** (после нормализации имён временных LTO-файлов `.map`
совпадает построчно). `bl-mchf.bin` при этом совпадает побайтно (одинаковый SHA-256), а
`fw-mchf.bin` отличается только внутри строки `UHSDR_BUILD_DAT` (`"fwt-"__DATE__"-"__TIME__`,
2–4 байта времени сборки в зависимости от цифр). Полное побайтовое совпадение прошивки между сборками невозможно
по определению; совпадение при повторной линковке без изменения исходников — см. §7.

## 4. Как это устроено (и чем отличается от `make`)

`tools/build.py` — маленький драйвер сборки на Python:

1. парсит `mchf-eclipse/include.mak`, `files.mak`, `bootloader.mak`, `f4-include.mak`,
   `f4-files.mak`, `f4-bootloader.mak` (переменные `SUBDIRS`, `HAL_SUBDIRS`, `SRC`, `HAL_SRC`,
   `DSPLIB_SRC`, `BL_SRC`, `BL_HAL_SRC`);
2. компилирует каждый файл теми же флагами, что и Makefile:
   - общие: `-mcpu=cortex-m4 -mfloat-abi=hard -mfpu=fpv4-sp-d16 -mthumb -DARM_MATH_CM4
     -DCORTEX_M4 -DSTM32F407xx -D__FPU_PRESENT=1U -DUSE_HAL_DRIVER -DDEBUG -DUSE_FULL_ASSERT
     -DTRACE -D_GNU_SOURCE -DTRX_ID="mchf" -DTRX_NAME="mcHF QRP" -ffunction-sections
     -fdata-sections -flto -Wall -Wno-unused-function -g3`;
   - прошивка: `-O2`;  загрузчик: `-Os -DBOOTLOADER_BUILD`;
   - все `-I` из `SUBDIRS` + `HAL_SUBDIRS`, `-std=gnu11` (C) / `-std=gnu++11` (C++);
3. линкует `g++` с `-flto --specs=nano.specs -g3 -Xlinker --gc-sections` и скриптом
   `linker/arm-gcc-link_f4_flash1024k.ld` (прошивка) или
   `linker/arm-gcc-link-bootloader_f4.ld` (загрузчик), библиотеки `-lm -lc -lnosys`;
4. делает `.bin`/`.hex` через `objcopy` и печатает расход flash/RAM.

Отличия от `make all` (осознанные, ничего не меняют в коде прошивки):

* целевые объекты строятся в `build/`, а не рядом с исходниками;
* `g++` при линковке получает список объектных файлов через response-файл `@build\firmware.link.rsp`
  (в Windows командная строка ограничена 32 767 символами, 528 путей туда не влезают) —
  результат линковки идентичен;
* добавлен `-fcommon` (совместимость с GCC ≥ 10, иначе LTO-линковка падает с
  `multiple definition of bm_set_normal / USBD_COMP_CfgDesc`);
* добавлены `-MMD -MP` — только для корректной инкрементальной сборки (файлы `.d`).
  Разбор `.d` в `tools/build.py` исправлен: зависимости — это Windows-пути с буквой диска
  (`E:\…`) и экранированными пробелами, а gcc/ld при `-MP` дописывает в конец файла phony-цели;
  прежний разбор «по первому двоеточию» молча терял все заголовки (правка только в драйвере,
  флаги не менялись);
* `-DTRX_NAME="mcHF QRP"` — без одинарных кавычек. Makefile задаёт `TRX_NAME='mcHF QRP'`,
  и после подстановки в строку получается `'mcHF QRP'` **вместе с кавычками** (они видны в
  строке версии); здесь строка чистая;
* не генерируются `.dfu` (скрипт `support/hex2dfu/hex2dfu.py` требует Python 2 и модуль
  `intelhex`) и handbook (`support/ui/menu/mk-menu-handbook`, bash) — для прошивки они не нужны.

### 4.1. Правки исходников для GCC 15.2.1 / binutils 2.45 (P0-2)

Проект 2018 года; на современном тулчейне он не собирался. Правки минимальные — **только типы,
прототипы и ассемблерные директивы; логика Nizar и P0-патчи не тронуты** (полный разбор — `_audit/dev/p-build.md`):

| Файл | Правка | Почему |
|---|---|---|
| `mchf-eclipse/files.mak` | + `iir_2_8k.c`, + `iir_16k5_96ks.c` (46 из 46 фильтров) | символы использовались, но файлы не компилировались — `undefined reference` |
| `drivers/audio/audio_driver.c:6414` | явный каст `(AudioSample_t *) srcUSB` | GCC ≥ 14: несовместимые типы в тернарном операторе — ошибка (буфер остаётся 16-битным, изменился только тип указателя) |
| `drivers/ui/menu/ui_menu.c:2254` | каст `(volatile uint8_t *) &ts.twenty_watt_meter` | `bool` = `int` (`uhsdr_types.h`), а меню-хелпер ждёт `uint8_t*`; значение всегда 0/1, порядок байт little-endian — поведение не меняется |
| `drivers/ui/ui_driver.h`, `ui_spectrum.h`, `ui_menu.h`, `audio_driver.h` | добавлены прототипы (4 функции) | GCC ≥ 14: неявное объявление — ошибка, а не предупреждение |
| `drivers/ui/ui_configuration.c` | `#include "ui_menu.h"` | для прототипа `UiMenu_Set_Spectrum_BackGround_color()` |
| `drivers/ui/lcd/ui_lcd_hy28.c:2345/2436` | прототипы `UiLcdHy28_WriteIndexSpi_Prepare_ILI9341/_ILI7789` | функции определены ниже первого использования |
| `misc/profiling.h` | `inline` → `static inline` (15 определений) | C99/C11 inline без внешнего определения; под LTO `profileTimedEventInit` не инлайнился — `undefined reference` |
| `basesw/mcHF/…/arm_bitreversal2.S` | `.type …, %function` | иначе символы NOTYPE с чётным адресом: линкер считает их ARM-кодом → `Unknown destination type (ARM/Thumb)` |

Проверенный набор правок для этой же кодовой линии (референс-репозиторий `Mchf_RS918`, коммит
`f64c8e1`) содержал также `extern` для `uwTick` (`stm32f4xx_hal.h/.c`), `extern` для
`OFDM_CONFIG_700D` (`codec2_ofdm.h`) и замену `arm_fill_q15` на `memset` в `audio_driver.c`.
Здесь **эти три правки не понадобились**: `uwTick`/`OFDM_CONFIG_700D` сливаются штатным
`-fcommon` и линковка проходит, а `arm_fill_q15` в этом (96 кГц) варианте кода отсутствует.
Лишних правок не вносилось.

В сборке остаются **предупреждения** (не блокируют): **v1.0** — 80 строк в `warnings.log`
(67 предупреждений компилятора, 64 уникальных текста + 13 строк линковки newlib-nano);
**v1.1/v1.2** — **78 строк** = fw 70 + bl 8 (64 предупреждения компилятора, 24 уникальных
текста + 14 строк линковки: 13 newlib-nano + 1 lto-wrapper). Этап A (v1.2) новых предупреждений
не добавил, ни одного на строках product-патчей.
Примеры компилятора
(`-Wcomment` — закомментированные блоки Nizar, `-Wvla-parameter`/array-parameter — FreeDV,
неиспользуемые переменные, формат `%ld`, `-Wattributes` в HAL и т.п.; все — в коде
Nizar/upstream/FatFs/CMSIS, ни одного в правках сборки) и предупреждения линковки newlib-nano
(`_close/_read/_write/... not implemented`). Полный список — `build/warnings.log`.
Файл `warnings.log` — артефакт сборки (в `.gitignore`, как и весь `build/`).

## 5. Как прошивать

### 5.1 Прошивка (firmware) — через загрузчик по USB, без программатора

Загрузчик UHSDR представляется компьютеру как USB-флешка и умеет сам обновлять прошивку
(см. `mchf-eclipse/src/bootloader/bootloader_main.c`, `Bootloader_UsbMSCDevice_Application`).

1. Выключить трансивер.
2. Нажать и **удерживать** кнопку **BAND−**, включить питание. На экране появится
   информация загрузчика (`Firmware Name: fw-mchf`). Кнопку BAND− держать.
3. Подключить USB-кабель к трансиверу — на компьютере появится съёмный диск.
4. Пока BAND− удерживается, загрузчик:
   * сохранит текущую прошивку в файл `fw-mchf.old` на этом диске;
   * если на диске лежит **`fw-mchf.bin`**, запишет его в flash (на экране
     `Updating firmware using "fw-mchf.bin"...`).
   Поэтому: скопируйте `build\fw-mchf.bin` в корень появившегося диска **до** того, как
   загрузчик начнёт обновление, либо положите файл заранее на SD-карту/диск.
5. Дождаться `Finished.`, отсоединить диск (или нажать BAND− для перезагрузки) — трансивер
   перезапустится с новой прошивкой.

Если BAND− **не** удерживать, загрузчик просто сохранит дамп flash и загрузит текущую
прошивку — это безопасный режим «ничего не менять».

### 5.2 Загрузчик (bootloader) — только программатором

Собранный загрузчик — **UHSDR bootloader 5.0.4** (`UHSDR_BOOT_VERS` в `src/uhsdr_version.h`,
исходники — upstream UHSDR 2.12.2); на экране при входе в режим обновления он печатает
`Version: 5.0.4`. Образ занимает 31 620 из 32 768 байт (запас 1 148 байт). Отличия от прежнего
4.1.2 (2.9.48): переход в прошивку/DFU выполняется через `UhsdrBl_JumpToApplication()` (отключение
прерываний, `HAL_RCC_DeInit()`, сброс NVIC — надёжнее старт прошивки), состояния перезагрузки
заданы enum `BOOT_REBOOT`/`BOOT_DFU`/`BOOT_FIRMWARE`, перед сбросом MCU добавлен `__DSB()`.
Совместимость с прошивкой 2.9.48 сохранена: старые точки входа (`bootloader_main`,
`BL_Application`, `mchfBl_CheckAndGoForDfuBoot`) — псевдонимы в `bootloader_main.h`, а признак
SBLA/SBLS в SRAM2 (его читает `drivers/audio/freedv_uhsdr.c`) по-прежнему выставляется.
Загрузчик 4.1.2 (2.9.48) тоже работает с этой прошивкой; менять его нужно только если он старее.

Загрузчик занимает первые 32 КиБ flash (`0x08000000`), поэтому обновляется либо по SWD, либо
через встроенный DFU STM32.

**Вариант A — ST-Link / SWD (рекомендуется):**

```powershell
# любым из инструментов, например STM32CubeProgrammer (GUI/CLI) или openocd:
STM32_Programmer_CLI.exe -c port=SWD -w build\bl-mchf.bin 0x08000000 -v -rst
```

**Вариант B — DFU (встроенный загрузчик STM32):**

1. Нажать и удерживать **BAND+**, включить питание → на экране `DFU`.
   Загрузчик установит признак и перезагрузится в системный DFU STM32
   (`Bootloader_CheckAndGoForBootTarget`, старое имя `mchfBl_CheckAndGoForDfuBoot`;
   после `__HAL_REMAPMEMORY_SYSTEMFLASH()` переход на адрес `0x00000000`).
2. На компьютере появится устройство `STM32 BOOTLOADER` (DFU). Залить `build\bl-mchf.bin`
   по адресу `0x08000000` (STM32CubeProgrammer: `-c port=USB1 -w build\bl-mchf.bin 0x08000000 -v -rst`).
   Для DfuSe нужен `.dfu` — этот скрипт его не делает (см. §4), используйте CubeProgrammer или `.hex`.

**Важно:** не отключайте питание во время записи загрузчика. Если загрузчик «окирпичен»,
трансивер всё равно поднимается через DFU (BAND+ при включении), т.к. DFU — это ROM STM32.

## 6. Диагностика

| Симптом | Что делать |
|---|---|
| `arm-none-eabi-gcc not found` | указать `--toolchain` или `ARM_GCC_BIN` (§1) |
| `compilation failed for ...` | в выводе будет полная команда и текст ошибки компилятора |
| `link failed for fw-mchf.elf` | то же; частые причины — забытый исходник в `*.mak` или дубликат глобального символа в заголовке |
| предупреждения | все они пишутся в `build\warnings.log`; v1.0 — 80 строк (67 предупреждений компилятора, 64 уникальных текста + 13 строк линковки newlib-nano), v1.1/v1.2 — 78 строк (fw 70 + bl 8: 64 предупреждения компилятора, 24 уникальных текста + 14 строк линковки: 13 newlib-nano + lto-wrapper); все — существующие в коде Nizar/upstream, ни одного на строках product-патчей; разбор — `_audit/dev/p-build.md` |
| непонятно, что собралось | `build\build-summary.json` (размеры), `build\fw-mchf.map` (карта), `build\compile_commands.json` |
| хочется повторить «как в Eclipse» | `python tools\build.py all --force -v` |
| изменился заголовок, а сборка ничего не пересобрала | не должно случаться (учёт `.d` исправлен, §4); принудительно — `--force` |

Требования к ресурсам: на полную пересборку нужно ~1–1,5 ГБ на диске (объектные файлы + ELF с
отладочной информацией) и ~1,5 ГБ RAM при `-j12`.

## 7. Ограничения

* `.dfu` не собирается (нужен Python 2 + `intelhex`); `.hex` собирается — его достаточно для
  STM32CubeProgrammer.
* Handbook/меню-граф (`make ...handbook`) не генерируются.
* Прошивка собирается **только под F4** (RS-918/mcHF): скрипт читает `f4-*.mak` и
  F4-скрипты линковки. В дереве при этом **остались** каталоги других платформ upstream
  (`basesw/ovi40` — F7, `basesw/ovi40-h7` — H7), их `f7-*.mak`/`h7-*.mak`, скрипты линковки
  F7/H7 и Eclipse-конфигурации OVI40 (`.cproject`). Они не удалялись, но этим продуктом не
  поддерживаются, не собираются и не проверялись; `Makefile` формально сохраняет ветки
  `BUILDFOR=F7/H7` (без `$(error)`). Чистка дерева от них — отдельная задача (P2).
* CCM-память занята на 96,9 % (63 476 из 65 536 байт, свободно 2 060; в v1.2 не выросла) — при добавлении буферов
  в CCM сборка упадёт на линковке; свободная RAM (128 КиБ) при этом ещё есть.
* Байт-в-байт воспроизводимость между полными пересборками не гарантируется: в прошивку
  зашивается `fwt-<__DATE__ __TIME__>` (`UHSDR_BUILD_DAT`). Проверено: две полные сборки
  подряд дают одинаковые размеры и **идентичную карту памяти**, `bl-mchf.bin` совпадает
  побайтно, а `fw-mchf.bin` отличается только 2–4 байтами времени сборки (см. §3).
* Сборка проверена только на Windows + xPack GNU Arm Embedded GCC 15.2.1 + Python 3.12;
  Linux/macOS не проверялись (скрипт написан кроссплатформенно, но пути и response-файлы
  рассчитаны на Windows).
* В `warnings.log` остаются предупреждения компилятора/линковки (см. §3/§4.1 и
  `_audit/dev/p-build.md`); `-Werror` не включался, чтобы не менять поведение Nizar.
